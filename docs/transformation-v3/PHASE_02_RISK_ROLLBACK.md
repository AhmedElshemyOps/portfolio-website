# H. Risk and rollback plan

| Risk | Control and evidence | Recovery |
| --- | --- | --- |
| Foundation changes affect shared chrome or demo styling (B1) | Preview component and demo routes separately. Scope tokens. Record generated CSS and shared HTML diff. | Revert template/token commit and regenerate using previous sources. |
| Professional claims drift from CV and profile (B2/B5) | Keep claim evidence and approval next to wording. Use attribution and scope. Preserve the current CV. | Revert profile/case presentation commit and regenerate. |
| Journeys or graph create broken, duplicate or overconfident links (B3) | Existing destinations only by default. Validate edges, classify evidence and check map/list parity. | Revert journey/edge source records and rebuild search/graph consumers. |
| Publishing rewrites bodies or shifts URLs, social assets or placement (B4) | Protect byte spans, text/heading/anchor/link tuples and live canonical/card inventories. Test disposable publication rollback. | Revert publisher and affected derived files together from the approved pre-batch revision. Restore protected originals from the pinned baseline if a diff shows corruption. |
| Demo interactions break after presentation changes (B5) | Check all four demos with pinned inputs and previous outputs. Exercise local storage, export and optional InfraQuote backend tests in fixtures only. | Revert case/shared shell changes. Confirm cached and fresh browsers return baseline outputs. |
| Search, consent, ads or caching regress (B6) | Validate exact sitemap/canonical/crawl evidence, clean browser consent states, policy/placement review, and offline/update flow. GA4 source configuration, live behavior and account ownership/data are separate findings. Same distinction applies to Search Console markers and live ads.txt vs account approval. Employer, CV and demo surfaces stay ad-free by default. | Disable only an approved feature via its reviewed configuration switch or revert the release commit. Restore prior asset/cache version under the runbook. Any production operation requires authorization. |
| Pages deploys while release validation fails (B6) | Require both push and PR full release checks, approval, release inventory and owner-controlled deployment. Audit Pages separately. | If a later authorized release fails, revert to the last approved known-good deployment commit and verify served bytes and smoke routes. Use the protected published baseline as reference until another revision is accepted. |

Before each authorized batch, record base SHA, affected paths, generated outputs, baseline results, reviewer and rollback point. Review the source and generated diffs together. Stop if protected wording, URL ownership, consent, project behavior, or release controls diverge unexpectedly. Maintain ITIL 4 decision, incident, problem, change, configuration and release records and an improvement backlog. No production change or rollback was executed in planning.
