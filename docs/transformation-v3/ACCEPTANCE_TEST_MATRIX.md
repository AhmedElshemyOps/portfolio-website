# G. Acceptance and test matrix

These are future acceptance checks. Planning validation covered branch comparison, source-path existence, route evidence, captured article headings and selected anchors. No current release suite, Lighthouse, assistive-technology matrix, account validation or project browser regression was run during planning.

## Baseline vs candidate procedure

Use the exact published master revision in a clean, isolated checkout with full history, Node 22, Python 3.12, pnpm 9.15.9 and the frozen lockfile. Record OS/runtime, fixture versions, test commands, inputs, exits and raw logs. Run read-only preflight, then `pnpm run check:health`, `pnpm run check:redesign` and targeted release scripts. Reproduce candidate checks in a separate checkout under identical conditions. The [recorded master job](https://github.com/AhmedElshemyOps/portfolio-website/actions/runs/42690328221/job/129408066664) found 32 failures and six errors across 197 Python tests. The [Soft Clay job](https://github.com/AhmedElshemyOps/portfolio-website/actions/runs/42808085230/job/129802299301) found 15 failures across 197 tests at a different revision. Keep these result sets separate. Classify by test ID, input, assertion and error signature. A new failure or changed signature is a regression until investigated. Fix stale fixture assumptions only with a documented cause and independent proof. Known baseline failures are triage work and do not waive required release gates.
